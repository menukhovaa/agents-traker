# Specification: Tracker

## 1. Данные задачи

Каждая задача MUST содержать:

- `id` — уникальный идентификатор.
- `title` — название задачи.
- `hours` — оценка времени в часах.
- `done` — логический статус выполнения.

## 2. Начальное состояние

При первом запуске MUST отображаться пример:

| Задача | Часы | done |
|---|---:|---|
| Чтение | 2 | true |
| Практика | 4 | false |
| Повторение | 2 | false |

Суммарные часы MUST равняться 8.
Выполненные часы MUST равняться 2.
Прогресс MUST равняться 25%.

Если реализовано сохранение в localStorage и существуют ранее сохранённые данные, они используются вместо стартового примера.

## 3. Управление задачами

- Пользователь MUST иметь возможность добавлять задачи.
- Пользователь MUST иметь возможность удалять задачи.
- Пользователь MUST иметь возможность переключать done.
- Все действия MUST изменять фактическое состояние данных.
- Интерфейс MUST отражать актуальное состояние.

### Scenario: Добавление

WHEN пользователь вводит корректное название и часы и нажимает добавление,
THEN новая задача появляется в данных и соответствующем списке с done=false.

### Scenario: Удаление

WHEN пользователь удаляет задачу,
THEN задача исчезает из данных и списка, а показатели пересчитываются.

### Scenario: Изменение статуса

WHEN пользователь переключает done,
THEN статус задачи меняется и показатели пересчитываются.

## 4. Валидация

- Название после trim MUST быть непустым.
- Часы MUST быть числом от 0,5 до 24 включительно.
- Шаг часов MUST составлять 0,5.
- Пустые часы MUST считаться ошибкой, а не нулём.
- Некорректная форма MUST NOT создавать задачу.
- Ошибка MUST отображаться рядом с соответствующим полем.
- При ошибке введённые значения MUST сохраняться в форме.

### Scenario: Некорректное название

WHEN пользователь вводит пустое название или только пробелы,
THEN задача не добавляется и рядом с названием отображается ошибка.

### Scenario: Некорректные часы

WHEN пользователь вводит пустые или отрицательные часы,
THEN задача не добавляется и рядом с полем часов отображается ошибка.

### Scenario: Часы вне диапазона или шага

WHEN часы превышают 24, меньше 0,5, не являются числом или не соответствуют шагу 0,5,
THEN задача не добавляется и отображается ошибка.

## 5. Фильтрация

Приложение MUST предоставлять фильтры:

- Все — все задачи.
- Активные — done=false.
- Готовые — done=true.

Фильтрация MUST влиять только на видимый список.

Итоговые часы, выполненные часы и прогресс MUST рассчитываться по всем задачам независимо от выбранного фильтра.

### Scenario: Фильтр активных

GIVEN стартовое состояние с прогрессом 25%,
WHEN пользователь включает фильтр «Активные»,
THEN отображаются только «Практика» и «Повторение»,
AND прогресс остаётся 25%.

## 6. Прогресс

Приложение MUST отображать:

- Суммарное количество часов всех задач.
- Суммарное количество часов выполненных задач.
- Прогресс в процентах.

Прогресс MUST рассчитываться как округлённое до целого значение отношения выполненных часов ко всем часам, умноженное на 100.

Если задач нет, суммарные часы, выполненные часы и прогресс MUST равняться нулю.

Результат MUST NOT содержать NaN или Infinity.

### Scenario: Выполнение «Практики»

GIVEN стартовое состояние,
WHEN пользователь отмечает «Практику» готовой,
THEN выполненные часы равны 6,
AND общие часы равны 8,
AND прогресс равен 75%.

### Scenario: Удаление всех задач

WHEN пользователь удаляет все задачи,
THEN список становится пустым,
AND общие часы равны 0,
AND выполненные часы равны 0,
AND прогресс равен 0%.

## 7. Интерфейс

- Интерфейс MUST быть читаем на ширине 390 px.
- Горизонтальный скролл MUST отсутствовать.
- Все поля и кнопки MUST иметь понятные подписи.
- Ошибки MUST отображаться возле соответствующих полей.
- Данные и показатели MUST обновляться после действий пользователя.

## 8. Автономность

- Реализации MUST NOT использовать CDN.
- Реализации MUST NOT использовать внешние библиотеки.
- Реализации MUST NOT требовать API-ключи.
- Вариант A MUST содержать все ресурсы в одном HTML-файле.
- Вариант B MUST использовать указанную структуру файлов.

## 9. Необязательное сохранение

Если реализован localStorage:

- Задачи SHOULD сохраняться после изменений.
- Сохранённые задачи SHOULD восстанавливаться при повторном открытии.
- При недоступности хранилища приложение MUST продолжать работу в памяти.
- Пользователь MUST видеть понятное сообщение о невозможности сохранения.
